## 1. What the product is

Lumen Studio is an AI product-photography web app for **fashion/apparel**. A client uploads **one plain photo of a garment** (a phone photo on any background) and gets studio-grade catalog and campaign images:

- **Six shot types:** Flat lay, Ghost mannequin, Hero, Detail/macro, Lifestyle, Packshot.
- **Up to 3 camera angles per run**, e.g. front, side, back. Each angle is generated separately.
- **Two Google image models race each other:** Nano Banana 2 and Nano Banana Pro, several takes each.
- **A fidelity judge scores every take** against the original photo (label/print, colour, cut, realism), and the best match **per angle** is flagged.
- **Follow-ups on any take:** edit by prompt, upscale to 2K/4K, transforms (new colourway, season swap, social crop, banner with copy space, fashion illustration), use as new source, download.

It's modelled on **masonry.so**: race several models, keep whichever one actually preserves the product.

It's sold **B2B to multiple clients on prepaid credits**. Kavya holds one Gemini API key and funds it. Clients see only credits and a percentage, **never money or cost**.

## 3. Business model

### 3.1 Plans (cumulative: higher plans include everything below)

| Plan | Shot types unlocked | Default credits in app | Client price (landing page) |
|---|---|---|---|
| **Basic** | Flat lay, Ghost mannequin | 300 | **₹10,000 for 300 credits**, one-time |
| **Pro** | + Hero, Detail/macro | 900 | "Let's talk" (quoted per client) |
| **Max** | + Lifestyle, Packshot | 2,500 | "Let's talk" (quoted per client) |

Credit grants are defaults. Admin can set any number per client and top up at any time.

### 3.2 Credit price list (what clients are charged, in credits)

Formula in code (`src/lib/plans.ts → creditCost`):
`credits = max(1, ceil(base × modelMultiplier × sizeMultiplier))`

| Component | Value |
|---|---|
| Base: Flat lay, Ghost mannequin | 1 per take |
| Base: Hero, Detail, Lifestyle, Packshot | 2 per take |
| Base: Edit by prompt | 1 |
| Base: Transform | 1 (always rendered at 1K) |
| Base: Upscale | 2 |
| Model: Nano Banana 2 (`gemini-3.1-flash-image`) | ×1 |
| Model: Nano Banana Pro (`gemini-3-pro-image`) | ×2 |
| Size: 1K / 2K / 4K | ×1 / ×2 / ×3 |
| Camera angles | Each extra angle repeats the whole run (`batchCost × angles`) |
| Failed generation | Refunded automatically (0) |

Worked values:

| Action | Credits |
|---|---|
| Flat lay, NB2, 1K, 1 take | 1 |
| Flat lay, NB Pro, 1K | 2 |
| Hero, NB Pro, 2K | 8 |
| Edit, NB Pro, 1K | 2 |
| Upscale 2K (NB2 / Pro) | 4 / 8 |
| Upscale 4K (always Pro) | 12 |
| **Default run:** flat lay, both models × 2 takes, 1K | **6** (4 images) |
| Same run from 3 angles | **18** (12 images) |

What 300 Basic credits buys: 300 flat-lay/ghost images on NB2 at 1K · 150 on NB Pro · 50 default runs (200 images) · 16 three-angle runs.

### 3.3 Internal cost calibration (never shown to clients)

- **1 credit ≈ at most ₹6 of real Gemini spend.** NB2 at 1K ≈ ₹5.9 per image. NB Pro at 1K ≈ ₹11.8 = 2 credits.
- Heavier work (2K, 4K, upscales) is priced above true cost, so the margin never inverts.
- At ₹10,000 for 300 credits, the worst-case Gemini cost of a fully used Basic pool is about **₹1,800**.
- Earlier, Kavya considered ₹1,000 for 300 credits. That was flagged as **below cost**, and she chose ₹10,000.

Gemini API list prices, as researched in Sep 2026 (verify before relying on them):

| Model | 1K | 2K | 4K |
|---|---|---|---|
| Nano Banana 2 (`gemini-3.1-flash-image`) | $0.067 | $0.101 | $0.151 |
| Nano Banana Pro (`gemini-3-pro-image`) | $0.134 | $0.134 | $0.24 |

Judge calls on a Flash model are negligible, roughly $0.001–0.002 each.

### 3.4 Hard business rules

- **Clients never see currency or cost.** The UI shows a credit count and a % ring only (`CreditMeter.tsx`).
- The admin "Note" field on each client is private, e.g. "paid ₹10,000 on 21 Sep".
- Credits are reserved **atomically before** the Gemini call and refunded on failure. Parallel takes can never overspend a pool.
- Pausing a client blocks both generation and sign-in.

## 6. How a request flows

1. **Every request** goes through `src/proxy.ts`:
   - Always open: `/unlock`, `/api/unlock`, `/api/logout`, `/admin/login`, `/api/admin/login`, `/_next/*`, `/favicon.ico`, `/icon*`, `/apple-icon*`.
   - `/admin*` and `/api/admin*` need a valid `lumen_admin` cookie. Otherwise pages redirect to `/admin/login` and APIs return 401.
   - Everything else needs a valid `lumen_client` cookie. Otherwise pages redirect to `/unlock?next=…` and APIs return 401.
   - The cookie is `<subject>.<HMAC-SHA256>`, where subject is a client id or `"admin"`. It's verified with `SESSION_SECRET` alone, so gating costs no database call.
2. **Studio loads** → `GET /api/me` → plan, allowed shot types, credits left and %.
3. **Generate** → `Studio.generate()` fans out **angles × models × takes** parallel `POST /api/generate` calls (mode `shot`). Each carries `angleId`, `seedHint` when takes > 1, and the source image.
4. **`/api/generate`**:
   - Auth → client active? → plan gate (a disallowed shot never reaches Gemini, 403 with `upgradeLabel`).
   - Build the prompt → `creditCost` → `spendCredits` (atomic `INCRBY` then roll back if over the pool; 402 if insufficient).
   - `generateImage` → re-encode as JPEG, stepping quality down until the base64 is ≤ 3.6 MB → return image + credits left.
   - On error: `refundCredits` and 502.
5. Each finished take → `POST /api/judge` with the original upload + take (both shrunk to 1280px) → score → the gallery marks the best per angle.

## 7. Data model (Upstash Redis)

Key prefix `lumen:`

| Key | Type | Contents |
|---|---|---|
| `lumen:clients` | Set | All client ids |
| `lumen:client:<id>` | JSON | `ClientRecord` (see below) |
| `lumen:client:<id>:used` | Integer | Credits used (atomic `INCRBY`) |
| `lumen:client:<id>:log` | List | Usage entries, JSON `{at, action, credits, model}`, newest first, trimmed to 500. Refunds are negative credits |
| `lumen:user:<username>` | String | Username → client id |
| `lumen:fail:<username>` | Integer, TTL 900s | Failed sign-in counter |

`ClientRecord`: `id` (slug of name), `name`, `username?` (lowercase), `passHash?`, `passSalt?`, `plan` (`basic|pro|max`), `creditsTotal`, `active`, `note?`, `createdAt`, `lastActiveAt?`.

- `creditsLeft = creditsTotal − used`. `percentLeft` is rounded.
- `passHash`/`passSalt` are stripped before anything leaves the server. The API exposes `hasLogin: boolean` instead.
- **Legacy:** v2 stored passcodes as `lumen:pass:<sha256>` → id. v3 no longer reads these. Those clients need "Set login".
- **In-memory fallback:** if no Redis env vars are present, everything lives in a per-process Map and is lost on restart. Admin shows a yellow "No database connected" banner.

## 8. Authentication and security

**Clients: username + passcode (v3)**

- Username: 3–32 chars, `[a-z0-9._-]`, starts with a letter or digit, stored lowercase.
- Passcode: minimum 6 chars (`MIN_PASSCODE`). Admin auto-generates 10 chars from an alphabet with no look-alike characters.
- Hash: **PBKDF2-SHA256, 120,000 iterations, 16-byte random salt per client**, via WebCrypto.
- Lockout: **8 failures per username → locked for 15 minutes** (HTTP 429). Unknown usernames still run a dummy hash, so timing doesn't reveal which usernames exist. A successful login or "Reset login" clears the counter.
- "Reset login" replaces the username and/or passcode and **revokes the old one immediately**.
- After creating a client or resetting a login, admin shows the passcode **once**, with a "Copy message for the client" button (link + username + passcode).

**Owner:** single `ADMIN_PASSCODE` env var, compared via HMAC (constant time), with a 600ms delay on failure. No lockout on the admin login yet.

**Cookies:** httpOnly, sameSite lax, secure in production, 30-day max age. Changing `SESSION_SECRET` signs everyone out.

### 9.3 Prompt construction (`buildPrompt`)

The prompt is these parts joined by blank lines: shot prompt, `CAMERA: …`, `LIGHTING: …`, `BACKGROUND / SETTING: …`, optional `ART DIRECTION: …`, then **`FIDELITY_RULES`**. With takes > 1, a `VARIATION n` line asks for a slightly different pose or composition.

**Camera-angle grammar** (this is also the basis of the old "camera-angle" skill). Every angle prompt states:

- camera height relative to the garment mid-line
- rotation (0°, 35°, 90°, 180°)
- tilt
- lens as a 35mm equivalent (85mm catalog, 50mm flat lay, 35mm hero/dutch, 100mm macro)
- framing (the garment fills about N% of the frame height)
- depth of field

Lighting prompts name the source, direction and white balance.

The old skill also had a symptom → fix table:

- Garbled label text → add an explicit "reproduce text exactly" rule.
- Floating product → add a contact-shadow instruction.

**`FIDELITY_RULES`** are appended to every prompt:

- Same physical product: colour, fabric, sheen, print scale and placement, seams, buttons, zips, labels, trims.
- Reproduce text and logos exactly. Never invent or alter them.
- Keep the matte/gloss level and drape.
- Don't change proportions, length, neckline or fit.
- Photorealistic. No artefacts, HDR look, watermark or added text.

**Edit / upscale / transform:**

- The take being changed is sent as image 1 and the **original upload** as image 2. The prompt says image 2 is ground truth only.
- Edits: "change ONLY what the instruction asks".
- Upscale: same framing, recover texture.
- The Social crop aspect ratio is parsed from the request text (e.g. "9:16").

### 9.4 Fidelity judge (`gemini.ts → judgeCandidate`)

The judge gets the reference and the candidate, and returns strict JSON with scores 0–10 for:

| Dimension | Weight |
|---|---|
| label (text/logos/prints) | 35% |
| colour (hue/finish) | 25% |
| shape (cut/trims/proportions) | 25% |
| realism | 15% |

- Invented or altered text must score ≤ 3.
- `overall = round(weighted × 10)`, giving 0–100.
- Verdict: the model's own if valid, else **keep ≥ 80, review ≥ 60, reject < 60**.
- Temperature 0.1, `responseMimeType: application/json`.

### 9.5 Demo mode

If neither `GEMINI_API_KEY` nor `GOOGLE_CLOUD_PROJECT` is set, generation returns coloured SVG placeholders and judge scores are random 60–100. A "Demo mode" badge shows in the header. Useful for UI work at no cost.

## 10. Large images: the HTTP 413 fix (v3)

**Cause:** Vercel limits function request and response bodies to **4.5 MB**. A transform on a 4K take sent the 4K image (~4.2 MB base64) plus the original, so Vercel returned 413 before the code ran.

**Fix (`src/lib/client.ts`):**

- Uploads are always re-encoded as **JPEG ≤ 1600px, q0.9** (PNGs too, with transparency flattened to white).
- `fitBody()` shrinks every image field in a generate request through the steps 2048/0.9 → 1600/0.86 → 1280/0.82 → 1024/0.78 until the JSON is ≤ 4.0 MB.
- The judge always receives both images at ≤ 1280px, q0.85.
- Friendly error messages for 413 and 504.

**Server (`/api/generate → compress`):** output is re-encoded as JPEG. Quality steps down (86→80→72→64 for images over 2200²) until base64 ≤ 3.6 MB, so 4K responses fit too.

**Verified:** reproduced with a worst-case 4K JPEG and a "turn this into royal blue" transform. The request went from over 4.5 MB to 1.7 MB and succeeded.

- **Purpose:** a page Kavya sends prospects before they buy. It covers what the product is, the problem, how it works, how fidelity is scored, the six shot types, plans and credit maths. It **never shows her cost.**
- **Hosting:** separate Vercel project from the same repo. Root Directory `landing`, Framework "Other", no build command.
- **Self-contained:** fonts are in `fonts/` (SIL OFL), illustrations are inline SVG, no external requests.
- **Config:**
  - `window.LUMEN_WHATSAPP = "91XXXXXXXXXX"` near the top of `<body>`. Digits only. Every CTA builds a `wa.me/<num>?text=<prefilled>` link from it.
  - `og:image` should become an absolute URL once the domain is known.
- **Sections (numbered eyebrows 01–07):**
  - Hero: "One product photo. A full catalog shoot." with an input → six-output animated visual.
  - 01 Why Lumen: shoots take days, reshoots multiply, generic AI changes your product.
  - 02 How it works: 3 steps.

**Fixes (22 Sep):** Upstash prefixed env vars (§11.3). `gemini-2.5-flash` deprecation (§11.4).

**v3 (23 Sep): current**

- **Removed the style description.** Kavya asked whether it could work reliably. The honest answer: fabric weight, fibre content and drape aren't visible in a single photo, so the fields most clients care about can't be reliably inferred. She chose to remove it.

## 15. Local development and testing

```bash
npm install
cp .env.example .env.local   # fill in values; leave GEMINI_API_KEY empty for demo mode
npm run dev                  # http://localhost:3000
npx tsc --noEmit && npx eslint src && npx next build   # must all pass before pushing
```

- Without KV variables, data is in memory, so restarting the server wipes clients.
- **Test approach used so far:** Playwright headless Chromium covering:
  - owner login → create client → client login (wrong passcode, then right)
  - upload → ghost mannequin with 3 angles (and a refused 4th) → generate 12 takes → detail → transform
  - 413 reproduction using route interception to inject a real 4K JPEG
  - brute-force lockout (8 × 401, then 429; other users unaffected)
  - mobile (390px) and desktop (1440px) screenshots, including the landing page
- When restarting a local server, make sure the old `next-server` process is really gone. Otherwise a stale process can serve chunks from a deleted `.next` folder and the page shows "This page couldn't load".

## 16. Known limitations and roadmap ideas

**Limitations**

- No admin brute-force lockout, only a 600ms delay.
- Takes run in parallel: up to 3 angles × 2 models × 3 takes = 18 simultaneous Gemini calls. Watch Gemini rate limits for big runs.
- Generated images live only in the browser session (no server storage). Refreshing the page loses the gallery. Clients should download what they keep.
- Credits have no expiry logic.
- `.gitignore` contains `.env*`, which also ignores `.env.example`.

**Ideas (from the README and discussions)**

- Per-client branding on the sign-in screen.
- Batch mode: a folder of SKUs → CSV of best-match images for Shopify import.
- Email or WhatsApp the client automatically when they drop below 10% credits.
- True transparent-PNG packshots via background removal.
- Multi-photo input (front/back/close-up/label) for better fidelity.
- Once NB Pro alone consistently scores "keep" on a product type, default to Pro only to halve cost, and re-add NB2 when the judge says review or reject.
- Save galleries server-side (e.g. Vercel Blob) so clients can come back to past runs.
